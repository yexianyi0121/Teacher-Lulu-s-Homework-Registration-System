## 二、逐条发现

### D-01 存储写满后继续录入：界面全部正常，刷新即回滚，警告条可被关掉

**严重度**：P1（丢数据，且事后完全无感知）

**复现步骤**
1. 正常录入 1 号 = A（确认已落盘）。
2. 把 `Storage.prototype.setItem` 对 `xq.state.v4` 改为抛 `QuotaExceededError`（等价于 localStorage 配额用尽——真实场景：历史记录累积到 5MB，或 `xq.corrupt.*` 堆积，见 D-14）。
3. 继续录入 2、3、4 号，全部打 A+。
4. 观察界面 → 关闭窗口 → 重新打开。

**实测行为**
- 第 3 步后界面：`["1A🙂✓","2A🙂✓","3A🙂✓","4A🙂✓"]`，**四格都显示成功**，无 toast、无红字。
- 磁盘 `xq.state.v4` 的 entries 仍然只有 `{"1":{...}}` —— 2/3/4 号从未写入。
- 唯一的提示是一条横幅：「⚠️ 浏览器存储不可用，刷新后数据会丢失，建议先导出备份 [知道了]」，**不是 toast，不阻断录入，点「知道了」即永久消失**（`storageDegraded` 只存在内存里，不写盘、不持久化）。
- 重新打开后：`["1A🙂✓","2","3","4"]` —— 2/3/4 号不见了，**且此后再也不会出现任何提示**（横幅条件已被重置）。
- IDB 快照在 30 秒窗口内为 `[]`（`SNAPSHOT_INTERVAL=30_000`），这段时间全丢。
- 首次打开即写满（`xq.state.v4` 从未写入）的情形同样：3 格全部显示成功，磁盘一直是 null。

**代码定位**
- `src/infra/storage.ts:121-141` `saveState()`：`localStorage.setItem(STORAGE_KEY, ...)` 的 `catch` 只 `return { ok:false }`，**丢弃了错误原因**，调用方无法区分"配额满 / 被禁用 / 其他"。
- `src/hooks/useAutoSave.ts:12-31` `flush()`：`ok=false` 且非 blocked 时只 `setStorageDegraded(true)`，**没有 toast、没有阻断录入、没有停止自动跳格**。
- `src/App.tsx:306-311`：`storageDegraded` 横幅的「知道了」= `setStorageDegraded(false)`，关掉之后不会重现。

**用户误解**
"格子打了勾、还弹了『2号 训练优秀 +3』，就是存上了。" —— 实际上从第一次写失败起，之后所有录入都是"内存里有效、磁盘上不存在"。老师当天照常关电脑，第二天打开就是回滚，而且没有任何线索告诉她丢了哪几格。

**建议修法**
1. `saveState` 返回失败原因（至少区分 `quota` / `denied` / `other`）。
2. 第一次写失败就弹**不可忽视的 toast + 持续红条**，并且**立刻暂停录入**（输入不进格子，或格子显示"未保存"角标），而不是继续假装成功。
3. `storageDegraded` 写入 sessionStorage 或 URL hash，**刷新后仍然提示**；「知道了」只隐藏横幅，不复位"降级中"状态。
4. 配额满时自动降级：把历史记录/旧记录搬到 IndexedDB（已有 `xq-backup` DB），保证当前记录一定能落盘。
5. 写失败时立刻把内存 state 落到 IDB 快照，作为兜底。

### D-02 两个窗口同时用：后写的整表覆盖先写的

**严重度**：P1（丢数据）

**复现步骤**
1. 窗口 A 录入 1、2、3 号（已落盘）。
2. 窗口 B（另一个标签页，或老师以为"另一台电脑"其实同一浏览器）录入 4、5、6 号。
3. 观察磁盘，然后关掉 A。

**实测行为**
- A 录完：磁盘 `{"1":"A","2":"A","3":"A"}`。
- B 打开时界面确实显示 `["1","2","3"]`（读到的是 A 的数据），但 B 的录入是**基于它自己内存里那份旧快照**，写盘时整表覆盖。
- B 录 4-6 后：磁盘变成 `{"4":"A+","5":"A+","6":"A+"}` —— **A 的 1-3 被静默整表覆盖，没有任何提示**。
- A 侧收到 toast「检测到另一个标签页修改了数据，建议刷新避免覆盖」，但**没有横幅、不阻止继续写**；A 的界面仍是 1-3 号（4-6 不可见）。
- 关掉 A（触发 pagehide flush）→ 磁盘又变回 `{"1":"A","2":"A","3":"A"}` —— **B 的 4-6 被 A 的旧快照覆盖**。
- 最终新开窗口看到：`["1","2","3","4A+😄✓","5A+😄✓","6A+😄✓"]`（内存态），**磁盘只有 4-6**。两个窗口各有一次写成功，最后一次写赢。

**代码定位**
- `src/hooks/useAutoSave.ts:61-65` `onStorage`：听到 `xq.*` 变化只 `showToast('检测到另一个标签页修改了数据，建议刷新避免覆盖')`，**不锁写、不合并、不刷新**。
- `src/infra/storageHealth.ts:57-67` `shouldBlockOverwrite()`：只拦"即将写入为空且磁盘非空"，**拦截不了"非空覆盖非空"**。
- `src/hooks/useAutoSave.ts:12-31` + `:83` 订阅：内存 state 是唯一真相，无版本号 / 无 `updatedAt` 比对 / 无 last-writer-wins 提示。

**用户误解**
"我在学校电脑上录完，回家再补几格，两边都有。" —— 实际上只有一个窗口的数据能活下来，且活下来的是"最后一次关窗/最后一次写入"的那个，老师完全无法预测。

**建议修法**
1. 写盘前先读磁盘 `lastSavedAt`，若比内存里的旧、且不是自己写的，**弹冲突对话框**（保留磁盘 / 保留内存 / 导出两份手工合并），而不是默默覆盖。
2. 加 `writerId`（sessionStorage 生成）+ 心跳锁：检测到另一个活跃写者时，**把当前页降为只读**并提示"另一个窗口正在使用，请关闭后再用"。
3. 至少把 storage 事件升级为**阻断性横幅**，而不是一条 3 秒就消失的 toast。

### D-03 页面任何一次"卸载"都会用内存旧快照覆盖磁盘

**严重度**：P1（丢数据）

**复现步骤**
1. 正常录入 1、2、3 号并确认落盘。
2. 在页面不产生任何录入动作的情况下，用外部手段修改磁盘上的 `xq.state.v4`（模拟：另一个窗口写入、同步软件写入、老师手工导入、崩溃前的半截写入被修复）。
3. 直接关闭窗口（不点任何按钮）。
4. 重新打开。

**实测行为**
- 场景 A：外部写入 `content:"EXT-CLOSE"`（长度 4031）→ 关窗 → 磁盘回到 4009 长度，`content=null`。**外部写入被抹掉。**
- 场景 B：外部**删除** 2 号格（磁盘 3880，只剩 1、3）→ 关窗 → 磁盘回到 4009，2 号格又回来了。也就是说，**内存里的旧快照会无条件覆盖磁盘**，无论磁盘那份是更新的、还是被修正过的。
- 触发点包括 `pagehide`、`beforeunload`、`visibilitychange → hidden`（`useAutoSave.ts:57-73`）。实测在 `page.close()` 时稳定复现。
- 反例（说明它是"卸载时"而非"任何时刻"）：单纯切走标签页（`visibilitychange`）在**没有脏数据时**不写盘——`onHide` 里 `flush()` 会执行，但 `saveState` 因为无变化……**实际仍会写**（见下），只是本次实测中因为写的是同一份内容所以看不出差别。真正危险的是：**只要内存和磁盘曾经分叉，任何一次切窗口/关窗口都会把磁盘改成内存那份。**

**代码定位**
- `src/hooks/useAutoSave.ts:55-73`：`onHide = () => { if (timer) clearTimeout(timer); flush(); }` 挂在 `pagehide` / `beforeunload` / `visibilitychange(hidden)` 上。
- `flush()`（`:12-31`）没有任何"磁盘是否被外部改过"的检查，直接 `saveState(内存 state)`。

**用户误解**
"我只是切出去看了眼微信。" —— 一次切窗就可能把另一个窗口刚写进去的数据覆盖掉；关窗时更是必然。

**建议修法**
1. `flush()` 前比较磁盘 `lastSavedAt` 与内存 `lastSavedAt`：**磁盘更新 → 不写**，改为提示冲突。
2. `onStorage` 收到事件时，**同步更新本地 `lastSavedAt` 基线**，避免后续 flush 误判。
3. 卸载路径（pagehide/beforeunload）只允许写"必要时"：内存有未落盘变更才写，否则完全不动磁盘。

### D-04 只读态的主按钮"导出当前数据"导出空白数据

**严重度**：P1（误导性，会让老师误以为已备份从而放弃恢复）

**复现步骤**
1. 正常录入 1、2、3 号，并用【设置 → 导出全部数据】导出真备份到桌面。
2. 让 `xq.state.v4` 变成坏数据（模拟浏览器崩溃/同步工具写坏/磁盘故障）。
3. 新开窗口 → 出现只读红条「⚠️ 数据读取失败，系统暂时进入只读模式……建议先下载原始数据，再点击「清空并重来」，之后用【设置 → 导入恢复】把备份导回来。」
4. 按提示点 **「导出当前数据」**。

**实测行为**
- 只读面板三个按钮依次是：`导出当前数据`、`下载原始数据`、`清空并重来`。**「导出当前数据」排在第一位**，天然是老师的第一选择。
- 点击后**没有任何新提示**（toast 还是那句"数据结构无法识别，已进入只读模式"），下载悄悄发生。
- 下载得到的文件实测 **5.7 KB，`records = 0`，`classes = ['三年二班']`** —— 是一份**空数据的备份**，不是学生的登记。
- 真正的原始坏数据在「下载原始数据」（实测 186 字节，就是那段坏 JSON 字符串）。
- 而在此状态下「清空并重来」会被 `shouldBlockOverwrite` 拦住（磁盘出现两条 `xq.blocked.*`，界面出现两条"已阻止覆盖"横幅），**老师按提示操作会陷入"提示→操作→被拦"的死循环**，必须自己找到【设置 → 导入恢复】把备份导回来才能脱困（实测这条路可行：导入后恢复 1A🙂✓/2A🙂✓/3A🙂✓，且刷新、关窗后都不再回滚）。

**代码定位**
- `src/App.tsx:264-300`：只读横幅三个按钮，`导出当前数据` 走 `downloadBlob(exportAllBlob(st.exportState()))`，而只读态下 `store` 是 `createEmptyState()`，**导出的必然是空态**。
- `src/App.tsx:238-262`：blockedOverwrite 横幅的「导出备份」同理，导出的是内存空态。

**用户误解**
"我按系统说的点了导出，备份到手了，那就可以清空重来了。" —— 拿到的是一份空备份，真数据还在磁盘上但已经"看不见"；如果她顺手又清空了别的东西，就真的没了。

**建议修法**
1. 只读态下**隐藏/禁用「导出当前数据」**，或改名为「导出空白模板（不含学生数据）」并加副标题说明。
2. 只读面板把 **「下载原始数据」提到第一位**并高亮为推荐操作。
3. 「清空并重来」在只读态下要么真的允许（并自动先下载原始数据），要么直接移除，避免"提示你去点，点了又被拦"。
4. 只读横幅直接给出下一步按钮「📥 从备份导入恢复」，不要绕到设置里。

### D-05 导入失败 / 导入空备份后界面清空但无警告条，看起来像成功

**严重度**：P2（严重困惑，易导致错误决策）

**复现步骤**
1. 本机录入 1、2、3 号。
2. 制造两份"坏备份"：① 只含部分记录的备份；② 一份**空的**备份（老师在某次空状态下导出的）。
3. 【设置 → 导入恢复】分别导入。

**实测行为**
- 导入空备份：确认框文案「备份含 **0** 条记录、0 条历史。导入会覆盖当前数据（导入前会自动留一份，可在设置里回退）。确定继续？」—— 这个"0 条"是**唯一**的警示，且没有任何红色/危险样式。
- 确认后：内存被换成空态 → `shouldBlockOverwrite` 拦截（因为磁盘非空）→ **界面格子变空**（`["1","2","3"]`），磁盘仍是原来的 `recs=1`。
- 关键问题：**`replaceState` 把 `readOnly` 和 `blockedOverwrite` 都重置了**，本次是 flush 时才被拦，所以横幅是"事后"才出现的；且**导入流程本身不检查"导入结果是否真的替换成功"**。
- 在本实验里最终有两条"已阻止覆盖"横幅（说明系统挡住了），但在真实的"磁盘恰好也是空的/首次使用"路径下，**导入空备份 = 直接进入空状态且毫无提示**。
- 导入"部分备份"（只有 1 条记录）：界面 `["1A🙂✓","2A🙂✓","3A🙂✓"]` 与导入前完全一致，**看不出导入是否生效**，也没有任何"导入成功"的明确反馈。

**代码定位**
- `src/components/modals/SettingsModal.tsx:363-390`：导入流程 `importAll` → `openConfirm` → onConfirm 里 `replaceState(parsed.state)`，**没有校验导入后的记录数与当前数据量的相对关系**，也没有在"导入的数据比现有数据少"时二次警示。
- `src/store/index.ts:116-137` `replaceState()`：清空 `undoStack/redoStack`、`readOnly=false`、`blockedOverwrite=false` —— 导入后连撤销上一状态的机会都没有。

**用户误解**
"导入框说确定继续，我确定了，格子还是空的，那我准备重新录。"

**建议修法**
1. 导入确认框显示：备份里的**班级名、导出时间、记录日期范围**（后端已有 `exportedAt` 字段），并当"备份记录数 < 当前记录数"时用危险色二次确认：**「这份备份比你现在的数据少，会丢 X 条记录」**。
2. 当导入内容为空时**直接拒绝**并提示"这份备份里没有数据"。
3. 导入完成后用 toast 明确汇报结果：`已导入 N 条记录 / M 条历史（来自 一年三班，2026-10-20 导出）`；若被覆盖保护拦截，明确说"未生效"。

### D-06 导出"假成功"：下载被拦也提示已导出，并重置 7 天提醒

**严重度**：P2

**复现步骤**
1. 钩掉 `HTMLAnchorElement.prototype.click`（等价于：浏览器拦截下载、下载目录无权限、老师点了取消、下载管理器弹出"保留/放弃"并选放弃）。
2. 点【设置 → 导出全部数据】。

**实测行为**
- 界面上照常弹出 toast「已导出完整备份（含班级、登记、积分、设置）」，**没有任何失败提示**。

### D-10 "清空全部数据"没有"先导出"门禁，且与它自己的文案矛盾

### D-12 历史 200 条上限静默丢弃第 201 条

### D-15 换端口/换打开方式时数据"消失"，警告只在当次可见

**严重度**：P2（困惑 + 误导）

**复现步骤**
1. 用 `http://127.0.0.1:4177/` 打开，录入 1、2、3 号。
2. 用 `http://localhost:4177/` 打开（换主机名 = 换 origin）。

**实测行为**
- 新 origin 下 `.cell` 是全空的 `["1","2","3"]`，localStorage 只有 `xq.env` 一个键，**`xq.state.v4` 完全不存在**。
- **没有任何横幅或 toast 提示"上次不是这个地址"** —— 因为 `main.tsx:29-35` 的逻辑是"读到 env 标记且 origin 不同才提示"，而新 origin 的 localStorage 是空的，读不到标记，**所以第一次永远不提示，反而把 `xq.env` 写成新地址，从此再也提示不了**。
- 相比之下，在**同一 origin 内**伪造一个"上次是 file://"的标记时，横幅确实会出：「⚠️ 你正在用另一种方式打开（数据存在各自空间；上次不是这个地址）。想找回旧数据请用【设置 → 数据 → 导入恢复】。[知道了]」，但**点「知道了」当次即消失，刷新不再出现**（`envMismatch` 只存内存，`uiSlice.ts:156-157`）。
- file:// 与 http:// 的隔离实测确认：`dist/启动学情登记系统.cmd` 用 `--app="file:///.../学情登记系统.html"` 打开（老师日常方式），与 http:// 端 storage **完全隔离**。

**代码定位**
- `src/main.tsx:29-35`：`const mark = readEnvMark(); if (mark && mark.origin && mark.origin !== origin) setEnvMismatch(true); writeEnvMark();` —— 标记先读后写，**新 origin 首次打开必然读不到，因此必然不提示**；而 `writeEnvMark()` 又立刻把"这次的新地址"盖上去，旧地址信息只剩在**旧 origin** 的 storage 里，新 origin 永远不知道。
- `src/App.tsx:231-235`：横幅「知道了」= `setEnvMismatch(false)`，不持久化。
- `src/infra/backup.ts:92-116`：`readEnvMark` / `writeEnvMark` 实现。

**用户误解**
"我打开怎么就空了，是不是数据没了？" —— 数据在另一个"空间"里，但系统这次没告诉她。

**建议修法**
1. 反向检测：**当 `xq.state.v4` 不存在、但用户曾经用过（比如 IndexedDB 里有快照、或 `xq.lastBackupAt` 存在）时，提示"这个地址下还没有数据，你可能是用另一种方式打开的"**。
2. 环境标记写到一个**跨 origin 可见**的地方（IndexedDB 不跨 origin，file:// 也不跨；可行方案：导出/导入引导 + 启动时的"没数据"提示）。
3. `envMismatch` 存 sessionStorage，刷新仍提示；「知道了」只隐藏横幅。
4. 把「【设置 → 数据 → 导入恢复】」做成启动横幅上的直接按钮。

## 三、做得好的地方（避免误伤）

修复时请保留这些行为，它们是当前系统的安全底线：

1. **每次录入立即落盘**：实测录入后 50ms 内磁盘已更新（`useAutoSave` 300ms 防抖实测在 50ms 就看到了，说明还有别的同步写路径），关窗瞬间的 flush 也可靠（录 5 号后立刻关窗，重开 5 号仍在）。
2. **覆盖保护 `shouldBlockOverwrite` 挡住了最坏的情况**：内存空 + 磁盘非空 → 拒绝写入并隔离原文（实测清空操作、清空历史失败导入都被正确拦截）。
3. **损坏时进入只读而非覆盖**：`xq.corrupt.*` 保留原文，界面进入只读并给出导出入口；恢复路径实测有效（导入备份后刷新、关窗均正常）。
4. **file:// 与 http:// 隔离符合预期**，且 dist 自带 file:// 启动脚本 + 内联 HTML，离线可用（实测 Service Worker 已注册，断网刷新后应用仍能启动、数据仍在）。
5. **容量足够**：真实结构下 46 人 × 30 天 × 20 历史 = 315 KB；即使 120 人 × 60 条记录 × 200 历史也只有约 4.1 MB，仍在 5MB 配额内——但**正因为接近上限，D-01/D-14 才是真问题**。
